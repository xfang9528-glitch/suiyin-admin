# DR-093: 变声语音展示必须同时满足租户与账号配置

## 类型
产品 / UX / 多租户

## 状态
已采纳

## 日期
2026-08-30

## 项目
碎银 PC / 艺星 PC / 碎银 APP（所有租户的变声语音通用门槛）

## 背景

双语音条用于让我方在一条已发送语音中同时回听原声，并在变声生成完成后核对客户实际听到的版本。但“产品支持变声”不等于每个租户、每个账号都已经启用变声器。如果只凭页面、仓库、租户名称或演示数据展示第二条语音，未配置变声的用户会看到无法成立的生成中、失败或变声后状态，还会多出无意义的占位空间。

## 决策

我们决定：

1. 变声能力可以覆盖所有租户，但一条我方语音是否展示变声槽位，必须同时满足：当前真实租户已开启变声能力，且当前发送账号 / 人设号已完成有效变声配置。
2. 只有两个条件都为真并且该消息被明确记录为进入变声流程时，才展示下方“变声生成中… / 变声生成失败 + 重试 / 变声后语音条”。
3. 任一条件为假、缺失、失效或无法确认时，一律按未配置处理：只展示既有单条原声，不展示第二语音条、生成状态、失败状态、重试入口、隐藏占位或预留间距。
4. 展示判断不得根据仓名、租户显示名、页面类型或 demo 会话硬编码推断；必须使用稳定租户键、稳定账号 / 人设号键和消息级“已进入变声流程”事实，并与会话、消息、任务和窗口上下文一起隔离。
5. 旧消息或缺少资格事实的消息不得反推为已配置；只有明确记录了变声流程事实的消息才可恢复对应状态。
6. 本决定只冻结原型与后续工程交付的行为合同，不授权在本工作区修改 Flutter / React / Go 等生产仓；生产实现仍须走正式 Issue、独立 worktree、Phase、PR 与房总 review。

## 后果

- **好的：**
  - 所有租户共享同一能力，不再靠租户名维护例外名单。
  - 未配置变声的租户或账号继续看到熟悉的单语音条，不会被不存在的处理状态误导。
  - 租户切换、账号切换和历史消息恢复都有稳定、可测试的资格边界。
- **代价：**
  - 发送与渲染链路需要同时取得租户级、账号级配置，并把是否进入变声流程固化到消息事实中。
  - 演示数据必须显式准备“两个条件都满足”和“任一条件不满足”的矩阵，不能默认全部消息有变声。

## 重新评估信号

- 产品改为只需要租户级或账号级任一配置即可变声。
- 账号配置被取消后，历史消息的回听政策需要改变。
- 变声能力从按账号配置改为消息级临时选择，并明确了新的确认交互。
