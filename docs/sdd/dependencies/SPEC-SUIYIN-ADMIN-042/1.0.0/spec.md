# 工作账号每日触达人数与发送消息统计

## 1. 审核摘要

- **用户问题**：管理者需要知道不同工作账号每天实际触达多少好友、成功发送多少消息，目前要等待较慢的逐账号日报采集，无法随时按部门和单日查看。
- **完成后变化**：在碎银管理页「数据展示」独立打开本页，可按部门和工作账号查看指定一天的触达人数及发送消息数；今天随新数据持续更新，昨天、前天与任意单日可直接查询。
- **本次范围**：独立统计入口、工作账号逐行展示、部门筛选、今天/昨天/前天/单日日期、最新 S/Q/B/C 口径及同集合的成功消息条数、数据完整状态、今日实时更新。
- **明确不做**：本工作区不实施 Flutter / React / Go 生产代码；不合并进原销售使用统计或 AI 辅助统计；不把员工合并行替代工作账号行；不新增销售考核、转化归因或聊天正文下钻。
- **需要房总拍板**：本次明确建单范围已由 2026-09-05 用户指令给出；工程可据此开展正式流程。新增业务口径须回到本规格。
- **AI 新提案**：30 秒自动刷新、正常链路目标 60 秒内可见，以及增量聚合/定期对账是工程建议，不冒充房总已确认的数值 SLA 或技术方案。

## 2. 用户问题与预期结果

### 2.1 用户与场景

- 用户角色：拥有管理页数据展示及对应部门/账号查看权限的管理者。
- 场景：白天看当前触达进度，或切换昨天、前天、指定日期复盘不同工作账号的工作量。
- 当前做法：只读日报枚举工作账号和好友历史，较慢且可能受分析账号权限、历史覆盖和统计核验差异影响。

### 2.2 用户问题

报告生成耗时，使管理者难以及时发现哪些工作账号触达少、哪些部门消息量发生变化；员工、工作账号、触达人数和消息条数也容易混淆。

### 2.3 完成后用户能感受到的变化

管理者在现有后台内选择一天、筛选部门，即可查看每个工作账号的成功发送量与去重触达人数，并知道数字截至何时、是否完整。

### 2.4 成功信号

| ID | 可观察信号 | 判定方式 |
|---|---|---|
| O001 | 同一员工两个工作账号分别占两行 | 测试数据和页面核对 |
| O002 | 今天的新成功消息会在页面自动更新 | 消息成功与页面出现时间对照 |
| O003 | 三来源触达可复算；跨来源同好友只在 C 计一次 | 小样本精确集合核验 |

## 3. 范围

- 「数据展示 → 工作账号触达与消息统计」独立入口，视觉与操作习惯参考销售使用统计。
- 一次选一个自然日；今天、昨天、前天快捷选择及单日日期控件；部门筛选；分页与全筛选结果汇总。
- 逐工作账号展示：日期、部门、工作账号/人设名称及可区分同名账号的标识、S/Q/B 各来源触达人数及成功消息数、综合去重触达 C、成功消息合计 M、数据截至时间与完整状态。

- 后端提供聚合统计并持续更新；今天无需等待晚间日报，也无需手动重跑 Codex。

- 跨天混为一行、跨工作账号合为一个员工主行、跨租户数据拼接、把客户自然人身份猜测用于去重。

- 把本报告的部分合计或未统计值当成固定验收金数；只统计文本消息的额外限制。
- 本次只创建正式工程 Issue 及交付合同；Flutter / React / Go 的实现、测试、CI、部署均由对应正式工程流程承接。

### 4.1 已发现冲突

- 既有日报按成员合并其唯一 persona；本次 E001 明确以人设号/工作账号为主维度。保持消息集合及来源定义，每个工作账号分别计算；员工合并值只能用于对应范围的报告对账。
- 旧报告/旧收集器有普通与企微混入、把手机个人微信 weChat 计入 S、仅按 salesName=手机企微识别 Q、群发候选只依赖 lastActiveTime 的历史问题；均不能作为本期统计逻辑。2026-09-04 修订 PDF 的严格 S 平台白名单优先；2026-09-05 PDF 中“S=非qw排除群发”的宽口径说明残留已过期。
- 原有 AI 辅助统计 #204 的“只含文本、上线后不追溯”是另一个功能的约束，本页不继承。
- 今日报告 S 官方值与历史集合不一致、存在权限覆盖缺口时，必须保留附件原始警示，不能宣称报告 C 已核验完整。
- 今日报告标注截至17:33:06，但生成时所用三来源字段的上界实为当日结束，Q/B合计不能声称严格对应该标注截止。详见附件说明；本期统计接口与页面水位必须严格一致。

## 5. 用户场景与验收

### US01 — 按部门、单日查看各工作账号

- **用户**：管理者。
- **前置条件**：拥有相应租户、部门、工作账号的统计权限。
- **目标**：快速查看当天或指定日的真实工作量。
- **独立价值**：无需等待人工日报即可比较工作账号。

#### AC-R001-01 — 独立入口与工作账号行

- Given 同一员工有两个工作账号，另有同名账号。
- When 打开数据展示的新入口。
- Then 两个账号分别展示，稳定标识可区分同名账号；原销售使用统计与 AI 辅助统计保持原含义。

#### AC-R002-01 — 日期边界与筛选

- Given 选中部门 A，存在前天、昨天、今天和跨零点消息。
- When 使用三项快捷日、单日日期以及切换部门。
- Then 每次只查选中自然日和部门，使用 Asia/Shanghai 的半开日区间；今天截至数据水位，历史日至次日零点，不跨日合并；异步旧查询不覆盖最后一次选定条件。

#### AC-R003-01 — 合格消息与来源分类

- Given 好友单聊消息混有成功、自方/客户方、群聊、失败、发送中、撤回、企微及群发记录。
- When 计算统计。
- Then 只含选中日自方 status=2 的好友单聊；Q 由 sendPlatform=qw 识别，不限 salesName；B 使用 adminWeb 与群发稳定标记；S 仅收经确认碎银客户端平台 windows/mac/android/ios；macOS 是展示名称，额外 API 枚举需先核实；weChat、未知/缺失来源及非群发 adminWeb 不进入三源主口径，各来源互斥。

#### AC-R004-01 — 人数去重与消息条数分开

- Given 一个工作账号向客户甲通过 S 成功发 2 条、Q 成功发 1 条，又通过 B 向客户乙成功发 2 条，数据完整且无重复记录。
- When 聚合。
- Then S/Q/B 人数=1/1/1，C=2；S/Q/B 消息数=2/1/2，M=5；重复回调、历史重复页不会增加数量，跨天及跨账号各自独立。

#### AC-R005-01 — 当日持续更新与迟到修正

- Given 今天页面已打开，出现新成功消息、重复回调及之后变为撤回的消息。
- When 自动更新完成。
- Then 数字按最新成功记录更新，重复不增计，status=6 退出主口径；页面显示实际数据截至时间，失败时保留旧数字并明确已过期，不冒充实时成功。

#### AC-R006-01 — 汇总、完整性和官方对账

- Given 多工作账号中有完整、无合格消息和来源缺失三类，且同一客户出现在两个账号。
- When 查看单账号与全筛选结果汇总，并与官方普通统计/两日报告比较。
- Then 完整空结果才为 0，来源缺失为未统计/不完整，C 与 M 仅在全部来源完整时成立；账号小计与部门唯一人数区分；S 在一致日期、账号、状态、来源范围下与官方统计核验，差异需定位并说明。

#### AC-R007-01 — 租户与权限

- Given 无权限账号、限制到部门 A 的管理员和另一租户。
- When 查询或改变筛选参数。
- Then 服务端及页面均限制可见范围；无权限、请求失败、同步不完整与完整零数据状态可区分，响应不包含客户身份/正文/其他租户数据。

### 6.1 不变量

- INV001：C 是人数并集，M 是消息条数；同一好友多条消息仅对消息数累加。
- INV002：两个人设号分别触达同一 customerId，各账号均可计1；账号小计不是部门唯一人数。
- INV003：群发只计好友历史中实际成功落地消息，筛选人数、任务数、任务成功数不替代好友消息集合。
- INV004：稳定 customerId 用于去重；不得通过姓名、手机号或昵称猜测同一自然人。
- INV005：Q 来源不以“手机企微”这一 salesName 文本限制；工作账号统计不要求把 Q 人工归给某个员工。
- INV006：weChat 是手机个人微信，不属于 S 或 Q；未知来源不得兜底计入 S。主表消息合计 M 仅为 S/Q/B 的成功条数，不暗示所有平台发送总量。

## 7. 状态与交互

- 首开/切日/切部门：立即呈现新筛选条件，加载后展示对应数据；结果必须标日期和水位。
- 今天自动刷新；过去日期展示该自然日数据，重查能反映迟到/撤回修正；切日不混合前后结果。
- 完整零数据、无筛选结果、无权限、查询失败、部分来源同步中分别呈现；错误可重试。
- 离开或关闭页停止该页自动刷新，重开默认今天；分页切换不改变全筛选结果汇总。
- 表格宽时横向滚动，数值对齐；工作账号标识不被截得无法区分。

## 8. 数据、权限与隐私

- 计算键包含 tenantId、自然日、稳定 persona/clientId；消息去重包含稳定消息ID及其必要命名空间。
- 触达去重用稳定 customerId；页面只返回计数，不直接返回客户名单或正文。
- 部门过滤沿用管理后台已有组织与工作账号归属逻辑，并在接口/测试说明中明确该逻辑；不把日报固定分组写死。
- 附件为用户明确要求交给梁晨的内部报告，只放私有 Issue 附件存储；原始采集JSON、Cookie、token、客户历史不上传。

只新增 Admin 展示，工作账号消息可来自现有碎银/企微/群发链路。来源判定一致，当前租户隔离；深圳艺星是验收数据来源，不允许从其他租户补数。
