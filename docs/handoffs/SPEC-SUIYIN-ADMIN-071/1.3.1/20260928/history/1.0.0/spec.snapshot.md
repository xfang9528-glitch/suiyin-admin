# 按部门与账号配置每日回访选中及排除规则

## 1. 审核摘要

- **用户问题**：运营每天重复找当天应该回访的人；不同部门、工作号和回访目的需要不同组合，逐次定制规则难以维护。
- **完成后变化**：管理者复用群发的账号选择、选中与排除维度，保存一套可重复使用的规则，另行启用并设每日运行时间；到回访日按当天数据筛出好友，有该好友所属账号接待权限的销售在自己的回访列表看到该好友，无权限的销售看不到。
- **本次范围**：先设计管理页规则配置、规则摘要、保存与启停的静态原型；新增独立规则与复制复用的设计提案，支持不同回访节点使用不同条件；明确部门、账号、时间、筛选语义，以及销售回访列表的账号接待权限可见性。房总已于2026-09-27批准先做一版静态原型；首轮实施深圳艺星，PC名单界面仍另期实施。
- **明确不做**：真实定时运行、私聊数据接入原型、PC 名单改造、自动发送、AI 个性化内容、分配机制和执行质检；这些作为后续切片，不把“已保存规则”说成“已生成真实名单”。
- **需要房总拍板**：本轮原型方向已批准；Q002–Q004以推荐值作为本地演示参数，Q005产品映射明确延期，Q006独立规则与复制已采纳。演示参数不代表生产业务口径已经定案。
- **AI 新提案**：以独立规则作为最小配置单位，相同条件可复制后调整回访节点，复制后互不联动；字段间选中取全部满足、排除取任一命中；日期增加相对回访日表达；保存默认未启用；按当前数据试算仅作演示；修改从下次运行生效。细节见 R001–R015；R014的账号接待权限可见性是用户已明确规则，上述方案由E015批准用于首版原型。

## 2. 用户问题与预期结果

### 2.1 用户与场景

- 管理者：按业务目的、账号所属部门/群组（渠道）和工作号配置规则，不必每次请人另写一套定制条件。部门在本规格中表示账号群组归属，不表示规则使用人员范围。
- 咨询师：后续上班在 PC 看到自己有接待权限账号下的应回访好友和入选原因，不再每天手工拼相同筛选；无该账号接待权限时看不到其应回访好友。
- 深圳实例：添加好友后按固定节点激活；近期已有联系时跳过本次；按产品决定后续沟通方向。
- 新增探索：相同筛选在不同回访节点可复用，节点之间需要差异时独立设置；深圳实例验证通用配置能力，不将其节点列表硬编码。

### 2.2 用户问题

一次群发通常处理当时筛出的名单。回访则需要每天重新回答“今天该找谁”，不能把配置当天的人保存成永久名单，也不能因中途聊天就错移固定添加周期。

### 2.3 完成后用户能感受到的变化

能看懂、检查、调整并重复使用一套选人规则；明确哪几个部门、哪些账号、哪些人会被选中或排除、下一次何时运行。

## 3. 范围

### 3.1 In Scope

- 管理页规则列表、新建/编辑、复制为独立规则提案、范围选择、两组筛选、日期表达、运行设置、摘要、保存/启停。
- 生效范围合并为一处账号选择，沿用群发“部门/群组（渠道） → 工作号”的操作；按群组选择或指定账号。不同渠道可以分别配置选中、排除和运行设置，不再单列咨询师使用部门。
- 同租户继承群发选中和排除维度，保留普通/艺星差异；不把医美维度强加给其他业态。
- 深圳首个规则示例和纯合成测试数据。可选“按今天试算”明确标为本地示例。
- 锁定后续PC可见性：应回访好友按所属工作账号接待权限进入销售回访列表；本轮只定义并验收合同，不扩展为PC页面实施。

### 4.1 已发现冲突

- 0.1.0将“生效部门”提案为人员范围并单独配置，已被E011明确纠正：本次部门就是账号的群组归属，合并到群发式账号选择。界面分组名称沿用本租户现有口径，不新增员工组织树。现有父渠道与单账号独立多选，匹配为渠道 OR 单账号；父渠道已选时取消子账号不等于排除子账号。长期成员变化仍由Q004处理，E011没有批准动态扩张范围。
- 账号级联设计文档写有确定/取消，当前实际是即时更新表单草稿。建议继承当前即时回填，由整个规则的保存/取消控制提交；R007。
- 群发固定日期区间无法独立表达每日重复的第 N 天条件。保留固定日期，增加相对日期；R004。
- 群发“双方发过消息”当前 mock 表示两方均发生过，不能当成访谈中的任一方发过。深圳用“我方2天 OR 对方2天”表达；R005。
- 群发至少勾选一名好友的提交守卫不迁到规则配置：规则当天命中0人仍可有效保存。原群发守卫及精确提示不改；R008。
- 旧回访类型、20:00全员兜底、兼职逾期、8分钟重分与本次无共同批准合同。仅作历史参考，本次不继承、不改旧稿。
- 旧 PC 未来30天 mock 名单不能代表回访日确定结果；未来只能描述计划，真实名单尚未生成。R012。
- 本轮用户授权新增设计，可以复用 PC 组件语义；不得称新增管理页是已采集的真实 Admin 页面。
- 0.1.2用一条规则的多个离散天数表达深圳节点，不能直接表达各节点不同的筛选。0.2.0提出独立规则为基本单位，复制后改时间条件；不强制新增“计划→节点”父子层，不自动拆分或联动旧规则。该调整已由E015批准用于首版原型；E013仅记录最初探索过程。

## 5. 用户场景与验收

### US01 — 管理者组合一套可复用规则

- 用户：有规则管理权限的管理员。前置：当前租户及可管理范围已明确。目标：按账号所属群组或指定账号配置选中和排除，独立价值是不同渠道可使用不同回访规则。

#### AC-R001-01 — 按账号群组配置不同渠道规则
- Given 演示账号甲属于渠道A，账号乙属于渠道B；管理者为两组分别保存不同筛选条件的规则。
- When 查看账号选择和两条规则摘要。
- Then 以同一“部门/群组（渠道） → 工作号”控件表达范围，两条规则各自作用于所选账号群组；可选择群组或指定其中部分账号；不存在另一个“供哪些咨询师部门使用”的字段。

#### AC-R002-01 — 两侧维度完整继承
- Given 在艺星演示租户新建规则。
- When 展开选中与排除条件。
- Then 与§6.3清单逐项一致，21项选中与26项排除均有对应入口；其他租户不硬套医美选项。

#### AC-R003-01 — 选中全部满足、排除任一命中
- Given 选中要求等级A与某需求，排除要求我方2天或对方2天有消息。
- When 对合成好友判断。
- Then 等级与需求必须同时命中；任一方向近期有消息均排除；已排除对象不被其他选中条件加回。

#### AC-R004-01 — 日期随回访日计算
- Given 添加日设为第0天，规则A选添加后第3天、规则B独立选第5天，合成好友添加日为9月24日。
- When 分别试算9月27日、28日、29日。
- Then 到期命中依次为A、无、B；不保存成三个绝对查询日期，不因中间消息改变添加锚点。该第0天口径是 Q002 提案，独立规则模型为Q006提案。

#### AC-R005-01 — 深圳实例任一方消息排除
- Given 好友今天处于第5天节点，近期仅对方发过消息，我方没发。
- When 运行示例判断。
- Then 今天排除；同理仅我方发过也排除；日后仍按原添加日期计算第7天节点，不重开周期。

#### AC-R009-01 — 账号选择与搜索不越界
- Given 已在渠道甲选账号1，又搜索当前渠道的账号2。
- When 对搜索结果全选或清空搜索。
- Then 搜索批量动作只影响当前可见结果，原先选择保留；所在账号的选中/排除条件均不得扩到规则范围外；账号选项不串租户。

### US02 — 保存后决定启用与运行时间

#### AC-R006-01 — 保存与启用分离
- Given 合法规则选择每天01:00、上海时区。
- When 仅保存，随后单独启用。
- Then 先处于未启用；启用后显示下一次计划时间；当前时间已过01:00时计划为次日，不补跑今日。页面同时标明仅本地演示。

#### AC-R007-01 — 编辑、取消与失败
- Given 已启用规则正在编辑。
- When 取消或模拟保存失败。
- Then 原已保存版本与启用状态保持，失败可重试；成功保存才替换规则版本，并从下一次计划运行使用新版本。重复提交不新增重复规则。

#### AC-R008-01 — 零命中不阻止保存
- Given 规则配置合法、今天示例数据命中0人。
- When 保存或查看试算。
- Then 允许保存；明确显示0人，不要求手工勾选一名好友；加载失败、无权限和字段未知不得显示为0人。

### US03 — 不因复用规则扩大权限或制造能力承诺

#### AC-R010-01 — 缺失数据不等于未联系
- Given 最近消息数据缺失，或指定账号权限已失效。
- When 预览命中与启用资格。
- Then 缺失数据标“无法判断”，失效范围明确提示并阻止带失效配置启用；不当成无消息，也不自动切成全部账号。

#### AC-R011-01 — 摘要可核对
- Given 配置账号群组/指定账号、添加节点及两条消息排除。
- When 查看摘要与示例试算。
- Then 摘要逐项呈现范围、节点、排除、运行时间及状态；示例显示入选/排除理由和试算基准时刻，不冒称真实人数。

#### AC-R012-01 — 配置和执行边界
- Given 管理页已在本地保存并启用示例规则。
- When 查看结果和未来日期。
- Then 不发消息、不调用真实调度；未来不显示已经确定的好友名单；规则不自动重新分配客户或改变部门成员可见权限。

#### AC-R013-01 — 租户与旧功能不串用
- Given 深圳和普通租户分别查看规则；旧群发仍在其原入口。
- When 切换租户、展开字段或打开旧群发。
- Then 部门、账号、选项、规则状态按租户隔离；医美示例不复制给普通租户；旧群发行为和零选人守卫保持。

#### AC-R014-01 — 销售只看到有账号接待权限的应回访好友
- Given 工作账号甲和乙均筛出应回访好友；销售A只有甲的接待权限，销售B只有乙的接待权限，销售C有甲乙两个账号的接待权限。
- When 各销售查看回访列表。
- Then A只看到甲下的应回访好友，B只看到乙下的应回访好友，C看到甲乙两者；同一规则选中两个账号也不扩大A或B权限。A失去甲权限后，后续展示/读取不得继续向A返回甲下好友；生成时曾有权限不构成后续访问授权。若同一联系人同时存在于两个账号下，有甲权限不能借此读取乙下的回访对象。

### US04 — 相同筛选复制，不同回访节点独立配置（原型已采纳）

- 用户：管理者。前置：已有一条保存的规则。目标：复用已有配置，再按不同节点调整；无需逐项重填，也不改变源规则。

#### AC-R015-01 — 副本独立，时间条件与每日运行时刻分开
- Given 规则A已启用，选添加后第3天、近2天任一方消息排除，每天01:00运行。
- When 复制A为草稿B，把添加天数改为第5天，把示例排除天数改为3天，保存后单独启用B。
- Then B保存前不参与任何运行，保存后先未启用；B有独立身份与配置，A仍是第3天/排除2天；A、B的每天01:00运行时刻没有因修改第几天而变化。再次改A或暂停B均不联动另一条规则。这里3天排除只作验证独立性的合成案例，不是深圳已确认实践。

#### AC-R015-02 — 取消复制及复制内容边界
- Given 管理者从已保存规则A发起复制。
- When 取消，或尝试重复提交同一个复制草稿。
- Then 取消不留下已保存副本，重复提交同一草稿最多产生一条新规则；副本仅带账号范围、时间/选中/排除条件、运行设置和目的说明，不带源身份、启用状态、真实名单、执行记录或权限。保存前展示完整摘要供检查，仍执行本租户范围与权限校验。

### 6.1 不变量

- INV001：规则存条件；每日结果是基于回访日的数据，不是配置时的固定人名快照。

### 6.4 不同时间节点的复用与独立配置（来源AI-PROPOSAL，原型已采纳）

最小对象仍叫“回访规则”，包含名称/目的、账号群组范围、选中条件（其中可含回访时间条件）、排除条件、每日运行时刻、状态。无需先新建一个父级计划才能创建规则；“一套回访安排”可以在业务上由多条规则组成，本期不新增强制父子结构或模板继承。

以深圳案例说明配置方法：先配置添加后第3天的规则；第5天沿用条件时复制后只改添加天数；第7天有差异时，在其独立规则里改选中或排除条件。以上第5/7天的配置方式是产品提案，访谈没有声称它们现有筛选不同。

“添加后第3天”本身属于时间筛选条件，不再让用户在另一处重复填写一份触发日期。用户复制后需要检查所有相关日期条件，不能让系统猜测哪些条件应随节点移动；UI不偷偷改动末次咨询等其他日期约束。

本期优先讨论单条复制；批量复制到多个节点、统一修改多个规则、模板与实例自动联动、同名计划分组均不默认加入。不同规则可能同日命中同一好友，复制不构成对重复生成/重复回访的授权，后续仍需完成R012所列执行去重合同。
